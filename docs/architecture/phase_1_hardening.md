# Phase 1 Architecture Hardening

## Scope

This hardening pass establishes infrastructure and dependency boundaries before feature implementation. It does not implement compression, batch processing, folder access, history, duplicate detection, smart analysis, or new feature screens.

## Decisions

### Feature-first Clean Architecture

The compressor feature owns its `data`, `domain`, and `presentation` boundaries. Domain contracts and use cases are independent of Flutter plugins. Data repositories are thin adapters over injected datasources. Presentation Providers will depend on use cases, never on plugins or repositories directly.

### Manual dependency injection

`lib/app/di/app_dependencies.dart` is the composition root for application services. Constructors receive interfaces, making each service independently testable. A future `injectable` migration is optional and must preserve explicit lifetime ownership.

### Result and AppError

`Result<T>` represents success/failure at domain and data boundaries. `AppError` provides stable codes, safe messages, optional causes/stack traces, and recoverability. Raw plugin exceptions must be translated at the data boundary.

### Startup and cache cleanup

Startup tasks run sequentially and stop on the first failure. Cache cleanup receives both a directory path and `FileSystemGateway`, allowing deterministic tests without touching the real filesystem. Cleanup only removes generated files with the application prefix and an age threshold.

### Image-processing port

`ImageProcessingRepository` and `ImageProcessingDataSource` isolate the future compression engine. A native package can later be replaced by another implementation without changing domain use cases or Providers.

### Localization

Flutter ARB generation is configured through `l10n.yaml`, with English and Hindi starter catalogs. Generated localization code is intentionally generated by the Flutter toolchain rather than hand-written. Domain code never consumes localized strings.

### Routing

`go_router` is configured behind `AppRouter.create`. Route locations remain centralized, while screen builders are supplied at composition time. This prevents routing from importing feature internals prematurely.

### Themes

Theme mode and theme variant are separate concepts. `AppThemeMode` supports system/light/dark, while `AppThemeVariant` leaves room for Material You and future custom themes. Design tokens remain in `core/theme`; app theme assembly remains in `app/theme`.

### Logging and performance

`AppLogger` is a replaceable interface. `ConsoleAppLogger` is enabled only when diagnostics are enabled. `PerformanceMonitor` has a no-op implementation and a debug implementation; it is not analytics or telemetry and never sends data off-device.

### Environment configuration

`AppConfig` distinguishes debug, profile, and release using Dart build-mode constants. Release logging and performance monitoring are disabled by default. No secrets or network configuration are introduced.

## Transitional legacy boundary

The original prototype remains under its previous paths until migration. `LegacyCompressorAdapter` is the only intentional application-boundary import of the old controller/screen, and the adapter is constructed by the DI graph. No other new infrastructure may import legacy code. Phase 2 will move the compressor Provider and screen into the target boundaries, then remove the legacy controller/services.

## Dependency graph

```text
main.dart
  -> AppDependencies
  -> StartupInitializationService
  -> PhotoCompressorApp

PhotoCompressorApp
  -> AppProviderScope
  -> AppRouter
  -> feature presentation (temporary legacy adapter only)

future Provider
  -> domain use case
  -> domain repository interface
  <- data repository implementation
  <- data datasource / platform adapter
```

No dependency points from domain to presentation, platform plugins, localization, or Android code are permitted.

## Test boundaries

- `test/core` tests Result, configuration, logging, performance, startup, and cleanup behavior.
- `test/features/compressor/domain` tests entities, repository contracts through fakes, and use cases.
- `test/features/compressor/data` tests datasources and repository adapters.
- `test/features/compressor/presentation` tests Providers and feature widgets.
- `test/goldens` contains UI snapshot tests isolated from unit tests.
- `integration_test` contains device-only picker, MediaStore, lifecycle, and large-image tests.
